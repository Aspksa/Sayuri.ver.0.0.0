# Архитектура Sayuri Yukishiro — v0.1.0

## 1. Слои

```text
«Sayuri Yukishiro.bat»              единственный вход для пользователя
        |
        v
scripts/launcher.ps1                поиск Python, записываемое хранилище, диагностика
        |
        v
sayuri_yukishiro.main               CLI: --preflight | --serve | --endpoint
        |
        +--> diagnostics            готовность машины и носителя
        +--> core.SystemCore        системное ядро
        |        |
        |        +--> configuration
        |        +--> logging
        |        +--> event_bus
        |        +--> job_manager
        |        +--> checkpoints
        |        +--> recovery
        |        +--> CoreAPI       единственный интерфейс для будущих модулей
        |
        +--> server                 локальный HTTP: web shell + JSON API
                 |
                 +--> web/                интерфейс
                 +--> data/core/          база ядра
                 +--> data/modules/       базы будущих модулей
                 +--> data/runtime/       endpoint.json: адрес и токен
```

Ядро не содержит прикладной логики. Оно отвечает за запуск, состояние, журнал, события, задачи и восстановление.

## 2. Правило переносимости

Ни один компонент не вправе предполагать букву диска или каталог установки. Все пути выводятся от корня проекта. Перенос каталога с одного носителя на другой не требует настройки.

Это проверяется тестами: исходники и лаунчеры не содержат жёстких путей вида `C:\`.

## 3. Носитель и SQLite

WAL быстрее, но файлы `-wal` и `-shm` рассинхронизируются с базой на синхронизируемых, сетевых и съёмных носителях. Поэтому режим журнала выбирается по типу носителя:

| Носитель | Режим | synchronous |
|---|---|---|
| локальный диск | WAL | NORMAL |
| съёмный, сетевой, синхронизируемый | DELETE | FULL |

Переопределение: `SAYURI_SQLITE_JOURNAL_MODE=WAL|DELETE`.

Соединение закрывается всегда: незакрытый handle на Windows не даёт безопасно извлечь носитель.

## 4. Хранилище

```text
data/
  core/sayuri_yukishiro.db    база ядра
  modules/<module_id>.db      база каждого будущего модуля
  runtime/endpoint.json       адрес, pid и токен текущего запуска
  logs/sayuri-core.log        журнал с ротацией
  cache/
```

Если носитель защищён от записи, лаунчер переносит `data/` в `%LOCALAPPDATA%\SayuriYukishiro\data` и сообщает об этом. Переопределение вручную: `SAYURI_DATA_DIR`.

## 5. Схема базы ядра

Миграции объявлены списком `MIGRATIONS` и применяются по порядку. База, содержащая неизвестную сборке миграцию, считается новее кода, и запуск отклоняется вместо тихой порчи данных.

| Версия | Содержимое |
|---|---|
| 1 | meta, modules, settings, events, audit_log |
| 2 | core_services, core_jobs, checkpoints |
| 3 | runtime_sessions — журнал запусков |

## 6. Жизненный цикл служб

Службы стартуют в порядке регистрации и останавливаются в обратном. Если служба не поднялась, уже запущенные останавливаются: частично поднятое ядро опаснее не поднятого.

Состояния: `created`, `starting`, `running`, `stopping`, `stopped`, `failed`. `HealthMonitor` сводит их к `healthy`, `degraded` или `failed`.

## 7. Запуск сайта

1. Проверяется, не запущен ли экземпляр с этого носителя: `endpoint.json` плюс проверка живости pid.
2. Сервер встаёт на штатный порт; если он занят, операционная система выдаёт свободный.
3. Фактический адрес и токен атомарно записываются в `endpoint.json`.
4. Отдельный поток ждёт, пока порт начнёт принимать соединения, и только тогда открывает браузер.
5. При выходе `endpoint.json` удаляется, строка запуска закрывается, ядро останавливается.

Повторный запуск `.bat` не поднимает второй экземпляр: лаунчер читает `endpoint.json` и открывает уже работающий сайт.

## 8. Безопасность

1. Сервер слушает только `127.0.0.1`.
2. `POST /api/shutdown` требует токен из `endpoint.json` и локального клиента.
3. Выход за пределы `web/` через `../` запрещён.
4. Токен не попадает в `/api/*` и в вывод `--endpoint`.
5. `quick_check` читает всю базу и выполняется только в глубоком статусе и диагностике, не на каждый опрос.
