# Обновление проекта — v0.3.0

## Что это

Обновление из GitHub, запускаемое с сайта. Устроено так, чтобы ответить на один вопрос: **может ли обновление сломать проект**. Ответ — нет, и ниже написано, чем это обеспечено.

## Слои

```text
web/index.html  раздел «Обновление проекта»
      |  GET /api/update, /api/update/plan, /api/update/progress, /api/update/history
      |  POST /api/update/check, /api/update/apply   (требуют токен)
      v
UpdateService
      |
      +--> checks.py      проверки готовности до установки
      +--> inventory.py   версии компонентов: было и стало
      +--> changelog.py   история из UPDATE_LOG.md
      +--> backup.py      копия базы и файлов состояния
      +--> git_client.py  только чтение и fast-forward
      |
      v
System Core: события, фоновые задачи, журнал обновлений в БД (схема v4)
```

## Пять защит от поломки

**1. Только fast-forward от источника текущей ветки.**
Источник берётся из настроенного upstream, а не из жёсткого `origin/main`: иначе обновление увело бы пользователя в чужую историю. Если история разошлась — обновление отклоняется с причиной `not_fast_forward`, автоматического слияния не происходит.

**2. Своя работа никогда не перезаписывается.**
Любые несохранённые правки в рабочем каталоге — блокирующий отказ с объяснением, что делать. `git reset` и force-операции в обёртке git отсутствуют как таковые, кроме единственного сценария отката (см. п. 5).

**3. Резервная копия до изменений.**
Копируются `VERSION`, `PROJECT_STATE.json`, `UPDATE_IDS.json`, `UPDATE_LOG.md` и база ядра. База копируется средствами SQLite (`conn.backup`), а не файловым копированием: во время записи обычная копия может оказаться нецелостной. Хранятся последние 5 копий.

**4. Проверка после установки — новым кодом, отдельным процессом.**
Запускаются валидатор протокола, компиляция и тесты. Отдельный процесс обязателен: текущий уже импортировал старые модули и проверял бы ими новый код.

**5. Откат при провале проверки.**
Файлы возвращаются к зафиксированному коммиту, база восстанавливается из копии. Миграции базы применяет новый код, и откатить их кодом нельзя — поэтому копия делается до установки, иначе «безопасный откат» был бы обещанием, а не фактом.

Откат разрешён в единственном случае: сразу после неудачного обновления, когда HEAD — именно тот коммит, в который обновление привело. Любое расхождение означает, что состояние уже изменилось, и тогда остановка безопаснее автоматического вмешательства.

## Стадии установки

| Стадия | Что делает | Что при отказе |
|---|---|---|
| Проверка готовности | повторяет проверки непосредственно перед установкой | установка не начинается |
| Резервная копия | снимает базу и файлы состояния | установка не начинается |
| Загрузка изменений | `git fetch` и сверка с планом | если источник ушёл вперёд — установка отклоняется |
| Установка | `git merge --ff-only` | статус `failed`, состояние не изменилось |
| Проверка после установки | протокол, компиляция, тесты | откат к предыдущему состоянию |
| Готово | фиксирует необходимость перезапуска | — |

Каждая стадия публикует событие `update.progress` с процентом, поэтому интерфейс показывает прогресс по факту, а не по таймеру.

## Почему источник сверяется дважды

Между проверкой и установкой проходит время — пользователь читает план. Если за это время источник ушёл вперёд, установка отклоняется с требованием проверить заново: иначе пользователь получил бы версию, план которой он не видел.

## Безопасность вызовов

`POST /api/update/check` и `POST /api/update/apply` требуют токен из `data/runtime/endpoint.json` и локального клиента — те же условия, что у остановки системы. Без этого любая страница в браузере или любой процесс на машине могли бы запустить обновление.

Токен выдаётся странице через `GET /api/session`. Чужая страница его не прочитает: ответ не содержит CORS-заголовков, а запрос с собственным заголовком требует preflight, который тоже не пройдёт. Локальный процесс и так может прочитать `endpoint.json`.

## Версии компонентов

Обновление показывает не одну цифру, а каждую часть, которая может измениться:

| Компонент | Источник версии |
|---|---|
| Проект | `VERSION` |
| Системное ядро | `CORE_VERSION` |
| Схема базы | номер последней миграции |
| Протокол обновлений | `schema_version` в `UPDATE_IDS.json` |
| Интерфейс, лаунчер, трей, точка входа | короткий отпечаток содержимого файла |

У лаунчера, трея и интерфейса нет своих номеров версий, поэтому для них считается отпечаток содержимого: пользователь видит, что файл изменится, даже если номера у него нет.

Для будущих модулей список расширяется тем же способом.

## История

История читается из `UPDATE_LOG.md`, который уже обязателен по протоколу: версия, дата, статус, изменения с их ID, результаты проверок, commit и следующий шаг. Второй, расходящийся список не ведётся.

Установки на этом носителе хранятся в таблице `update_runs` центральной базы: что на что менялось, какие стадии прошли, был ли откат и какая копия создана.

## Что обновление не делает

1. **Не перезапускает ядро.** Работающий процесс — всё ещё старый код; решение о перезапуске за пользователем.
2. **Не обновляет ZIP-копию.** Скачанный архив не является рабочей копией Git — это блокирующий отказ с объяснением.
3. **Не сливает разошедшуюся историю.** Только вперёд по той же истории.
